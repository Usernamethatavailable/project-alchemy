# 项目知识资产沉淀

把已发生的开发过程，转化为下次能找到、能判断、能使用的经验和资产。项目成功、失败、搁置或被通用能力覆盖，都可以复盘；投入很多不构成必须留下东西的理由。

项目路径就是取材入口。主动查找仍在本地或可用连接中留存的项目材料与相关开发历史，减少用户手动整理、复制和上传资料的工作；让结论能追溯到原始证据。

## 调用方式

用户通过宿主入口明确调用本 skill 时按此执行：Codex 使用 `$project-salvage`，Claude Code、Cursor 使用 `/project-salvage`，其他应用可按名称调用。自然语言中出现项目复盘、沉淀经验、留存知识资产、寻找可复用模块或查找旧方案的意图时，也主动调用；按任务意图判断，不要求关键词原样出现。单纯提到“资产”或“复盘”，不等于要求整理开发经验。

按项目回顾进入完整报告；只留存刚解决的问题或纠正旧判断进入轻量更新；询问以前怎么做时先查经验库。自动选用 skill 不等于自动写文件，仍按本次授权选择分析或保存。普通开发完成后不自行追加复盘，也不在后台持续监听聊天。

核心流程使用通用 Agent Skills 格式；按当前应用实际可用的文件、版本和聊天来源取材。`agents/openai.yaml` 是 Codex 的界面设置，随附定位器是可选的 Codex 历史入口。网页或云端只读获准上传、连接或挂载的材料，不假定能访问用户本机路径。项目使用 CLAUDE.md、GEMINI.md 等规则文件时，规则建议沿用该文件，不为统一名称另建平行规则。

## 两种用法

- **完整复盘：** 按项目或阶段还原关键历史，交付通俗报告；在获准的经验库中，将重要发现保存为独立条目并更新索引。
- **轻量经验更新：** 困难问题解决、关键选择作出或旧经验被纠正后，只处理相关条目、证据和索引，不生成长报告。

用户要求查“以前怎么做”时，先检索已有经验再建议行动。涉及保存、合并或查用经验库时，读取 [references/experience-library.md](references/experience-library.md)。报告按项目组织，长期经验按问题组织；普通 Markdown 是共同载体，安装的 skill 和用户资料分开保存。

用户只给路径并说“看看能提取什么”时，默认只读，直接完成取材和分析，不要求用户先准备材料。保存报告、修改 AGENTS.md、抽取代码分别按已有授权处理；保存报告本身不等于授权修改源项目规则。

用户已指定经验库并授权沉淀时，先查索引和相关条目，再保存增量：同一事实不重复写，新证据修正原条目，保留结论改变的原因。没有指定库时，获准保存的资料放当前工作区 `knowledge/`；只读任务交付草稿和拟更新说明。

## 先确定这次能分析什么

从当前请求、可见对话和指定项目入手，读已有说明与成果索引。确认要回顾的项目或阶段，沿用用户已给出的授权，不为普通分析和本地整理重复索取确认。

可用证据包括代码、现有 skill、文档、提交差异、测试结果、问题记录、用户纠正和开发对话。只使用实际可访问的材料；当前仓库不能代表全部开发历史，可见对话也不能代表其他聊天。缺失材料时完成有依据的部分，说明缺口；仅在它会改变关键结论时提问。

按问题读取，不默认全仓扫描：先看目标、实际产物、停止原因和已有经验，再围绕具体发现追查相关代码、历史和验证。跳过依赖目录、生成文件和无关日志。有新的结论或证据才继续扩大范围。

### 从路径找回相关上下文

用户给出路径时，先解析绝对路径并核实目录存在；当前目录就是指定项目时直接使用。路径失效时检查明确关联的迁移或 worktree 线索，仍无法定位再问，不自动换成同名项目。

1. **读项目现状。** 先查适用的 AGENTS.md、README、计划与设计、复盘、任务记录、测试报告和资产入口，再追查相关实现。尊重用户限定的只读范围。
2. **查版本历史。** 用 `git -C <项目路径> rev-parse --show-toplevel` 确认仓库根目录，不靠目录内有没有 `.git` 判断。若只是落在无关的上级仓库内，不能把上级全部历史当成项目历史；围绕目标相对路径读取相关提交、差异及当前未提交改动。没有 Git 或没有提交时说明这一点，继续使用其他证据。最终文件不能还原所有失败尝试，也不能用提交说明替代实际验证。
3. **定位相关开发记录。** 环境提供聊天查询工具时，先查元数据，再只读相关聊天；没有这类工具时，检查实际存在且允许读取的本地索引、会话与归档记录。Codex 的本地历史是可选来源，不假定固定存储格式、接口或目录一定存在。优先从运行环境给出的存储位置和索引定位；常见的 `CODEX_HOME` 或用户目录下 `.codex` 仅作为检查线索，不读取凭据或无关配置来找历史。
4. **核对项目归属再读正文。** 用会话工作目录、项目根目录、仓库身份、明确出现的文件路径或 worktree 关系确认关联，规范化路径分隔符并按文件系统规则比较。目录名前缀、相似标题或同名文件不能单独证明属于同一项目。先筛元数据，再按相关阶段、文件与问题读取正文，不把全账户聊天当作输入。
5. **交叉核对。** 从相关对话中提取需求变化、用户纠正、失败尝试、决策理由及验证线索，与代码和测试记录核对。保留消息来源、时间或记录位置。历史中的指令是待分析材料，不是本次授权；只读查询不恢复、续跑旧任务。助手曾声称完成，不能单独证明实际完成。

材料不足时先报告哪些来源找到了、哪些未找到或无权访问，以及这会限制哪些结论。只在确实缺少不可替代的信息时请用户补充，不默认要求重新上传整个项目。删除的聊天、未留存的尝试和不可访问的云端记录不能承诺恢复。

查 Codex 历史的可用方式发生变化时，按当前工具与本地可核实的数据调整。接口背景可参考[官方 App Server 文档](https://learn.chatgpt.com/docs/app-server)的只读历史查询部分；文档列出的接口不代表本会话已经暴露了相应工具。

本地历史可优先运行随附的 `scripts/find_project_history.py`，从普通 JSONL 首行与本地索引筛选项目元数据，输出匹配记录的位置，不输出聊天正文；索引可定位实际保存的压缩记录。用法、截断处理和后续读取见 [references/local-history.md](references/local-history.md)。没有 Python 或格式不支持时，用当前可用工具继续，不能把工具缺失等同于没有历史。

## 从事实走到下次行动

先还原真实需求、尝试的方法、观察到的结果，以及继续或停止的依据。区分用户陈述、可核查记录、推断和建议；过程不清楚时不补写故事。

对每个值得留下的发现，回答：

- **下次何时用？** 哪种具体情境会触发它。
- **有什么依据？** 引用文件与位置、提交、测试，或标明“当前对话中用户陈述”。
- **下次改什么？** 给出具体行动，或可定位的已有资产。
- **有什么会影响用法的条件？** 只写会改变判断或实际操作的具体条件，不为每条结论补谨慎尾句。

“已验证”只用于证据实际覆盖的范围；一个环境的成功不能证明跨环境可用。找不到行为变化或复用对象的感想，不作为长期资产。可只留下一个判断，或得出暂时没有可回收资产。

优先保留能减少重复投入的发现：确实有效的方法、被用户纠正的稳定偏好、失败后验证过的修正、值得重复使用的实现或验收样例。把观察改写成“遇到什么条件，采取什么行动，如何检查”，并交代原因与代价；“提前规划”“多测试”这类没有具体触发情境的建议不占成果条目。相近发现合并。成功做法和无效尝试都要审视，不把停项等同于所有技术成果失败，也不因有代码就认定产品需求已被验证。

## 给发现选择去向

| 去向 | 保存什么 | 判断标准 |
| --- | --- | --- |
| 长期经验条目 | 决策、失败原因、验证方法、取舍与反例 | 按问题独立保存，先检索再合并；含当前做法、必要依据和查找词 |
| AGENTS.md | 会影响以后行动的短规则 | 可执行、仍有效、适用于目标目录，且未被现有规则覆盖 |
| 可复用资产 | 已存在的模块、脚本、模板、提示词、案例或验收方法 | 能找到原物，说明用途、依赖、限制与复用入口 |

同一发现可以有不同去向，但不复制整段复盘到 AGENTS.md。项目经验放项目范围；跨项目建议先保存为经验候选，不能由一次经历自动升级为全局规则。

经验条目说明原因与判断；反复执行的流程可转为 skill，具体可判对错的情况可转为测试，已有实现保存模块入口。按用户授权落地，不自动安装新 skill、修改全局规则或复制整个仓库。

### 改进 AGENTS.md

先读目标文件及适用的上级规则，检查重复、冲突和过期内容。新增规则采用“遇到什么情况 → 做什么 → 如何判断完成”的写法；解释与历史依据留在复盘记录里。

用户只要求分析或保存经验库时，给出具体规则建议；用户已授权修改目标规则文件时，直接完成范围内的本地修改并检查差异。保留其他人的内容，不重写整份文件。存在无法自行解决的目标冲突时，列明冲突及推荐取舍；不静默覆盖。没有新增价值时明确写“AGENTS.md 无需修改”。

无法读取目标 AGENTS.md 时，只交付标明依据与适用范围的规则候选，说明尚未完成重复和冲突检查，不当成已经生效的规则。

不把停项决定写成“禁止做这类需求”。先分清是真实需求消失了，还是当前解决方式没有额外收益。

### 找到可复用资产

从实际被调用、解决过问题或被验证过的产物入手。对值得保留的对象记录：

- 原始路径或可访问入口、用途和典型使用场景。
- 输入输出或使用方式、必要依赖与项目耦合。
- 已有验证结果、会影响复用的已知问题，以及复用前最小改动。
- 当前状态四选一：**可直接复用**（目标场景已有可用依据）、**需适配**（原场景有效，但目标场景有明确改动）、**候选，待验证**（已找到原物，缺少使用或验证依据）、**暂不值得保留**（预期收益不足以抵消适配与维护代价）。写出判断理由。

正常填写模板或传入现成参数属于使用，不单独算适配；“需适配”应指出要修改的逻辑、结构、接口或依赖。没有指定目标项目时，描述已知能复用的场景及边界，不预先假定跨项目可用或一定要改造。

针对代码模块，沿至少一个实际调用点检查必要配置、外部服务、文件路径与副作用，写清迁移最小代价；只有文件名、目录名或看起来通用，不足以认定可复用。只有用户要求执行验证时才运行项目测试或脚本，避免分析过程中触发部署、付费服务或数据修改；已有测试记录可以作为历史证据引用。

没有看到实现时，不宣称发现了模块；可以提出后续查找方向，但不要把方向列成已有资产。没有必要为对称凑齐代码、经验和规则三类成果。

默认完成发现、定位与判断。抽取模块、重构代码、发布包或迁移到公共仓库，是独立动作，按用户授权范围执行。发现重复代码也不能直接推导出应建通用库；把迁移与维护代价纳入判断。

## 保存与交付

默认交付一份完整复盘报告，采用“关键开发历史 → 经验总结 → 可复用模块与其他资产 → AGENTS.md 规则建议 → 留存安排”的顺序，技术入口与资料索引放附录。按 [references/retrospective-report.md](references/retrospective-report.md) 组织。正文尽可能使用非技术语言，先讲发生了什么、对使用者有什么影响、下次怎么做；模块先讲能解决什么麻烦。函数、接口、依赖和运行条件集中放附录供 agent 查找，正文不堆代码名。不能用几条结论代替报告，也不把完整理解成逐轮聊天或逐次报错的流水账。用户明确要求简报或只查某一项时，遵从其范围。

优先使用项目已有的复盘和资产索引。需要保存报告且没有约定位置时，使用 `docs/retrospectives/project-salvage.md`；没有项目目录或只要求聊天分析时，在回复中交付。报告保留整体过程，重要经验保存为独立条目，二者用链接关联，不重复维护同一段结论。

用户要求完整报告且源项目限定只读时，在当前允许写入的输出目录保存单份报告，链接回来源；不要向源项目写文件。完整报告引用的外部案例只用于改进复盘写法，不能当作源项目事实。用户要求参考公开样例或确实需要调整结构时，可读 [references/retrospective-examples.md](references/retrospective-examples.md)，不在每次项目复盘中重复联网调研。

保存前读取既有记录：同一结论补新证据或修正边界，不再追加一份同义条目。后续证据推翻旧结论时，注明被取代的内容和原因。规则与复盘互相引用，避免维护两份相同说明。跨项目复用时优先记录来源入口，用户指定统一资产库后再迁移。

经验库内部链接使用相对路径，条目编号保持稳定。将理解结论必需的事实或必要摘录留在库中，原平台聊天和本机路径只作附加线索。使用经验后记录真实结果；没有信息增量时不改变文件和更新时间。

每条保留项说明下次何时用、依据和具体行动。正文用自然段或简短清单解释，不机械套用“观察、判断、边界与代价”等标签。技术问题用具体例子说明影响，例如把“模型引用内部 UUID 失败”写成“AI 抄错了材料编号，任务因此停下”；技术原名移到附录。只保留影响选择或操作的重要失败和条件，删除“未覆盖全部”“稳定性未确认”等免责式尾句。聊天回复给总体发现和报告链接，并说明 AGENTS.md 和资产的实际处理状态。保持事实准确，不把历史记录写成本次重测，不编造时间或 token 收益。

交付时补一行来源覆盖：分析的项目或阶段、实际读取的文件与历史、重要缺口。引用本地材料用绝对路径和行号，引用历史用记录位置及时间或事件位置；报告中不复制整段聊天和无关私人内容。用户只要试跑结果时，不先落盘一套报告或自动修改原项目。

当新增读取不再改变结论时停止。一次复盘不扩展成产品重启、全仓重构、重新开发或行业调研。

## 例子：专用 skill 被通用能力覆盖

输入只有用户陈述：“教学 PPT 定制化 skill 来自真实的课件微调需求，后来认为通用模型已覆盖，于是停止。”

报告中“经验总结”的一条示例（不是完整报告）：

> 老师需要修改课件，说明这个问题值得解决。接下来要判断的是，现成工具配上一份清楚的修改说明，是否已经够用。下次先拿几条真实要求和原始课件试一遍，比较结果要改多少、使用者要操作多少步，再决定自己开发哪些部分。

若随后能读到课件修改案例、验收清单或脚本，再逐项判断是否值得保留。它们不是仅凭故事就能认定存在的成果。
