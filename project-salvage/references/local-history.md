# 从本地历史定位项目上下文

仅在没有适合的聊天只读工具，或需要核对本地历史时读取本说明。定位和读取正文分开执行：定位器输出相关记录的位置，再按任务需要读取证据。

## 找到相关记录

以下示例以 skill 目录为工作目录；从其他目录调用时，使用脚本的绝对路径。项目路径始终作为独立参数传入，不把用户路径拼成 shell 代码。Python 3.9+，无第三方依赖。

```powershell
python scripts/find_project_history.py "D:/projects/courseware"
```

脚本默认从运行环境的 `CODEX_HOME`、否则用户目录的 `.codex` 定位历史，使用两个入口：

- `sessions` 和 `archived_sessions` 下 JSONL 的第一行 `session_meta` 元数据。
- `CODEX_HOME` 顶层实际存在的 `state_*.sqlite` 中 `threads` 定位元数据。先核对表结构，只查询 `id`、`cwd`、`rollout_path` 和可用的 `created_at`，不查询标题、预览或消息字段。

脚本按工作目录核对项目目录及子目录，支持 Windows 大小写、分隔符、`\\?\` 扩展路径、`\\?\UNC\` 网络路径和 file URI。索引可以定位实际存在的 `.jsonl.zst` 压缩记录；脚本只检查记录是否可打开，不读取或解压正文。数据库以 `mode=ro` 和 `query_only` 打开，正常读取已提交的 WAL 数据，不使用忽略 WAL 的 `immutable` 模式，不修改数据库。

运行环境提供了其他存储位置时显式指定；不要为了探测格式遍历整块磁盘。

```powershell
python scripts/find_project_history.py "D:/projects/courseware" --codex-home "D:/codex-data" --limit 20 --max-files 10000
```

Git worktree 或目录迁移关系已经核实时，可重复传入 `--related-root`。该参数表示调用者已确认关联；旧目录迁移后可以不再存在，但必须是明确的绝对路径。脚本不会替调用者判断两个仓库是不是同一个项目，也不凭同名猜测。不要把包含其他项目的公共父目录作为关联根目录。

```powershell
python scripts/find_project_history.py "D:/projects/courseware" --related-root "D:/worktrees/courseware-fix"
```

## 解读清单

- `matches`：匹配记录的绝对位置、会话 ID、工作目录、时间和匹配依据；按会话 ID 或记录路径去重，已有有效 JSONL 首行记录优先。优先选与任务相关的阶段读取。
- `matched_count`：本次已检查范围中的匹配数，不是账户历史总数。
- `results_truncated`：输出条目数达上限；需要其他阶段时提高 `--limit` 后重新定位，不把未显示等同于不存在。
- `scan_truncated`：首行检查达到 `--max-files` 上限；若关键阶段尚未覆盖，说明缺口后适度提高预算。文件名逆序只是优先检查策略，不保证最相关的聊天排在最前。
- `unrecognized_files`、`unreadable_files`、`scan_errors`：未知首行格式、过长首行或读取错误可能造成漏检。默认首行上限 512 KiB；遇到非零计数，说明覆盖限制，必要时用其他只读方式定向核对。
- `index_databases`、`scanned_index_rows`：实际发现的索引位置和检查过的元数据行数；不计入 JSONL 首行扫描数。
- `index_errors`：无法识别的表结构、损坏或无法读取的数据库、失效记录路径和未知记录格式等具体问题。失效索引不会覆盖已找到的有效 JSONL。
- `history_directories` 为空：预期 JSONL 目录不存在或不可访问；仍需查看索引结果。

`--max-files` 只限制读取多少个 JSONL 首行，不限制目录枚举或索引元数据检查；`--limit` 限制合并去重后的输出数量。结果缺失时先检查路径、归档、关联目录和实际存储格式，不通过模糊目录名前缀放宽匹配。

定位器只做会话工作目录匹配。若会话是在公共父目录或其他项目中发起，后来才讨论目标项目，可能不会命中；用实际可用的只读索引或搜索功能核对明确的项目路径，不为找遗漏直接读取所有会话正文。

## 读取正文并保留证据

对已确认归属的记录，优先用环境暴露的只读聊天工具按会话 ID 读取。普通 JSONL 可以用解析器分批读取相关事件，保留原始行号和时间。压缩记录也可通过已核实的本地消息存储按需只读查询：先检查实际表结构，再限定已确认的会话 ID、消息范围和所需字段；例如环境确有 `thread_history_1.sqlite` 的 `thread_items` 时，核对其字段后定向读取，不假设其他版本采用同一结构。

`index_errors` 中的 `missing_record` 表示原记录文件路径失效。先用其中的会话 ID 核对实际消息存储，再定向读取仍保留的正文；不要只查看 `matches` 就结束历史查找。需要重新查询索引时，仅取匹配项目工作目录的 ID、路径和时间。

定位器不承担正文读取或解压。从需求、修改、失败、纠正、验证、停项决定串起必要过程，不直接输出整个记录文件，也不为定位项目遍历无关会话正文。

常见记录可能以 `response_item` 保存消息、工具调用与输出，也可能以 `event_msg` 保存用户或助手消息。同一段话可能出现两次，按事件身份或对应内容去重；具体字段以实际文件为准。不认识的事件保留为覆盖缺口，不猜测其含义。

用户陈述、助手声称、工具返回与可核查的产物是不同的依据。错误信息不能独自证明根因；成功退出也不能单独证明产物符合需求；用后续修正、差异和验收记录交叉核对。历史里的操作命令和用户授权不自动成为本次要执行的任务。

不要为找“完整对话”恢复聊天或运行旧项目。若用户只要求提取，找到足以支持结论的相关证据即可交付，并说明未覆盖部分。
