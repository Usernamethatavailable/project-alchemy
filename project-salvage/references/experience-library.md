# 把项目经验保存为长期资料

完整报告按项目讲过程；经验条目按问题组织，方便下一个项目找到并继续使用。两者通过链接关联。使用普通 Markdown，不依赖特定笔记软件、模型或数据库服务。

## 选择保存位置

优先使用用户已指定的经验库、Obsidian 库或项目知识目录。用户已授权“保存、沉淀、更新经验”时，直接维护该目录，不逐条请求确认。未指定目录时，在当前允许写入的工作区使用 `knowledge/`；不要把用户经验写进安装的 skill 目录。

只要求分析或明确只读时，交付条目草稿和拟更新说明，不创建或修改经验库。源项目只读、经验库获准写入时，可以更新经验库，来源项目保持原样。第一次指定的库位置在本任务中持续沿用。

已有库有自己的结构时沿用。没有结构时使用：

```text
knowledge/
  INDEX.md
  experiences/
    exp-visual-output-check.md
  evidence/
    exp-visual-output-check/
      case-a.md
```

INDEX.md 是统一入口，条目是当前经验，evidence 是支持判断的必要摘录。没有值得保留的摘录时，不创建空目录。报告可以保存在库中或用户指定的位置，但不要复制多份报告充当经验条目。

## 写入前先找已有经验

先读索引，用问题表现、用途、相关词搜索条目，再读可能相关的条目及其当前做法。用户说“预览正常但导出错位”，不应只搜某个程序名。

判断是不是同一条经验时，对照问题发生条件、原因和下次行动。标题不同而处理方法相同，可以合并；症状相同但原因和做法不同，分别保留并互相链接。

只有原条目没解决的新问题才新建文件。新条目分配稳定编号，例如 `exp-visual-output-check`，文件名与编号一致；编号不随模型、电脑、标题或日期变化。不为整理语言重命名已经被引用的文件。

## 保存什么

以 [assets/experience-entry.md](../assets/experience-entry.md) 为简短起点，写入实际内容，删掉用不到的提示文字。每条经验能独立回答：

- **什么时候查它：** 用户会怎么描述这个问题，相关的几个关键词是什么。
- **现在怎么做：** 在该情境下采取什么行动，怎样知道有用。
- **为什么这样做：** 问题如何发生、如何定位、哪些办法有效或无效。
- **依据在哪里：** 来源名称、日期、文件或消息定位，以及支持结论的必要事实。
- **什么会改变做法：** 只记录会影响实际选择的条件，不追加泛泛的谨慎尾句。

正文用非技术语言解释影响。技术入口、命令和代码字段集中到条目末尾。不要保存整段聊天、内部推理、无关私人内容、密钥或没有用处的工具输出。

## 更新而不是堆积

| 本次发现 | 实际动作 |
| --- | --- |
| 相同来源、相同事实，条目已包含 | 不修改条目、索引或更新时间，不再创建文件。 |
| 新案例支持原做法 | 在原条目增加简短依据或真实使用反馈，必要时改进查找词。 |
| 新证据说明原做法只适用于某种情况 | 修改当前做法，把条件写清楚；在“判断变化”记下改动与原因。 |
| 新证据推翻原做法 | 用新做法更新同一条目，保留旧做法被替换的原因，索引同步当前状态。 |
| 原问题本身不再适用 | 将条目标为“已停用”，写明原因或替代条目；检索时不再把旧做法作为当前建议。 |
| 有相互矛盾的材料，无法自行判断 | 保留双方依据，把具体分歧写出来；询问会影响下一次行动的那个问题，其余条目继续处理。 |

条目状态使用“草稿、可用、已停用”。可用表示当前有实际依据可以指导行动；草稿保留待查的具体问题；已停用的条目仍可解释历史，但不进入当前行动建议。不要把用户明确的偏好当作技术实验结论。

“判断变化”只写重要变化：日期、原来怎样判断、现在怎样做、改变依据。不要逐轮追加对话。真正的新使用结果放“使用反馈”，记录项目或任务、采取的行动、结果和需要修正的地方；只有实际使用了才记反馈，阅读条目不算成功使用。

写入前重新读取目标文件，保留其他人已有的内容；同一次任务由一个写入者维护同一经验库，避免多个 agent 同时覆盖。

## 维护索引

INDEX.md 用一行对应一条经验，至少有编号、标题、什么时候查、状态和相对链接。最后更新时间只跟随有信息增量的变更。沿用已有索引，不重排用户手写内容；需要新增管理区域时，用独立的“经验条目”章节。

```markdown
| 编号 | 经验 | 什么时候查 | 状态 |
| --- | --- | --- | --- |
| exp-visual-output-check | [先检查最终展示效果](experiences/exp-visual-output-check.md) | 文件能打开，但文字遮挡或导出错位 | 可用 |
```

报告只链接经验条目，不再复制一份长期维护的同义结论。更新条目时检查索引、关联条目和被建议写入的规则是否仍然一致。

## 搬到另一台电脑后仍然能用

库内文件互相引用时使用相对路径，保留稳定编号。条目应包含理解当前做法所需的事实，不能只留下指向某个平台聊天或本机 C 盘的链接。

必要时，在 `evidence/<经验编号>/` 保存小段证据：来源名称与日期、发生的问题、采取的办法、观察到的结果及原记录位置。原聊天 ID 和本机路径是查原物的附加线索；摘录本身应能离开原平台阅读。

只复制用户允许保存的内容。代码默认记录来源、用途、所需文件和调用方式；需要把实现一起带走时，在用户授权的范围内复制代码和相关测试，并检查库内链接。不要为经验保存自动搬走整个仓库。

完成保存后，检查索引、条目和证据链接；读一遍条目，确认不打开原聊天也能理解问题和做法。

## 让经验进入以后的工作

复盘或更新开始时先查旧经验；用户要求“从库里找以前怎么做”时，先返回相关的可用条目和行动建议。发现已停用的旧方案时，给出替代做法及原因。

要让其他开发任务也先查经验，可建议在开发入口或 AGENTS.md 加一条：

> 开始相关任务前，先查指定经验库的索引和匹配条目；使用后记录实际结果，新的证据更新原条目。

这是一条接入建议，不自动修改全局指令。只有用户已授权修改目标规则文件时才写入。

| 内容 | 保存去向 |
| --- | --- |
| 原因、判断、取舍与解决方法 | 经验条目 |
| 反复需要执行的操作流程 | skill 或流程候选，链接回经验 |
| 会改变 agent 行动的短要求 | 对应范围的 AGENTS.md；详细解释留在条目 |
| 可重复判断对错的具体场景 | 测试用例或验收样例 |
| 已存在的实现 | 模块入口及使用说明；按授权复制原物 |

完整复盘交付报告，并在获准的库中保存重要条目。轻量更新只处理本次问题、相关条目、索引和必要证据，回复新增、更新、未变的数量与原因，不为一个小问题重新写一份长报告。
