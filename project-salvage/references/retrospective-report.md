# 完整项目复盘报告

用于默认的项目复盘交付。目标是让开发者理解关键决策，让后续 agent 能定位经验和资产；不是写项目宣传或给所有工作打分。

## 写给谁以及怎么写

正文写给主要通过自然语言与 agent 开发的人。先说明事情与影响，再解释原因和下一次做法。读者不用理解源代码，也应能看懂项目为什么转向、问题造成什么后果、留下的能力能替自己省什么事。

遇到技术内容，用具体场景解释。例如“内部 UUID 引用错误”写成“AI 抄错了材料编号，整个任务停了”；“渲染质量门”写成“先把新页面显示出来，再检查文字是否挤出边框”。确实需要保留技术名称时，集中放到附录，提供文件、函数、输入输出和使用条件。

直接陈述结果，删除反复提醒“不代表全部”“稳定性未确认”“不能保证”等尾句。关键失败要具体写清，例如“最后一次测试停在安排插入位置，没有生成文件”。不要把同一条提醒重复贴在每个结果后面。

## 标题和基本信息

标题直接说明项目与复盘用途。用少量信息写清项目路径、覆盖阶段、报告日期和截至当前的状态。把“用户决定停止”与“技术上已证明不可行”分开；日期跨度不能换算成投入工时、成本或 token。

## 一 关键开发历史

从真实需求讲到当前结局，优先用表格：

| 时间或阶段 | 发生了什么 | 为什么改变做法 | 结果 |
| --- | --- | --- | --- |

通常选择约 5—10 个真正改变方向的节点，材料少时更少，长项目按阶段归并。选立项、发现关键约束、方法变化、首次真实验收、反复失败的转折、范围调整及停止或交付决定；不列全部对话、代码提交和重试。

解释为什么当时的选择有其依据，再说明后续观察如何改变判断，避免用后来的知识责怪当时决策。没有日期时写阶段或“时间未记录”；区分事件发生时间和文档更新时间。

## 二 经验总结

先简短对照原始目标与实际结果，再归纳最有价值的成功做法和失败经验。不要为了覆盖所有类别而凑条目。

每条经验用两三段连起来：当时发生什么、给使用者或开发过程带来什么影响、下次遇到同类情况怎样做。用具体记录支持判断。只在会改变行动时说明必要条件或代价，不强行给每条经验增加一段限制说明，也不机械重复“观察、判断、边界”等标签。

可以涉及产品选择、需求和范围、技术方案、验证方法、开发者与 agent 协作，但只保留有本项目依据的内容。技术运行成功、符合用户要求、实际采用和商业验证是不同结果。校验器本身的误报与漏报也属于需核对的证据。

## 三 可复用模块与其他资产

先写确实存在的对象，再判断如何复用。代码按模块或可独立带走的组合归并；不要逐文件点名充数。正文优先用通俗表格，回答“现成能力是什么、能解决什么麻烦、下次怎么用”，再给出留存优先级。

技术附录为需要继续开发的 agent 提供：

- 名称、用途、典型场景和可点击的实际入口。
- 输入输出或调用方式，必要依赖、配置及副作用。
- 证据与状态：可直接复用、需适配、候选待验证、暂不值得保留。
- 最小复用动作、需重验的范围和明确不支持的情况。

复用判断以已有事实为依据；正常填写模板或传参数不算改造。使用条件写成具体动作，例如“运行前准备原始课件”“需要安装用于预览的程序”，不用泛泛的“仍需验证”代替说明。报告末尾统一说明本次做了什么，不在每个模块重复。

非代码资产可包含原始需求、评测协议、成功与失败样例、验收标准和操作流程。区分原始文件、指纹、输出结果及脱敏记录；客户原件不复制进报告。架构设想不是已经实现的模块。

## 四 AGENTS.md 规则建议

先读已有文件和适用的工程基线，说明已有规则覆盖了什么，再给少量真正新增或需要修订的规则。每条规则写触发情境、行动和完成标准，注明项目范围还是跨项目经验候选。详细历史留在报告，AGENTS.md 用入口链接与短规则承接。

只读任务交付建议，不实际修改。不能访问目标文件时说明候选尚未做重复与冲突核对。没有新增价值时明确无需修改，不为完整报告强行增加规则。

开发历史体现出稳定用户偏好时，在本节单列全局指令修改方案，包含来源、实际全局目标、修改前后原文、冲突取舍与条目编号。按 [global-preferences.md](global-preferences.md) 处理批准与写入；项目规则建议、待批准方案和已写入条目分别交代清楚。

## 五 留存安排与附录

把回收建议整理成小表：保留什么、落到哪里、复用前最小工作、当前是否已经执行。按下一次使用价值排序；不把复盘自动扩展为新产品开发、抽取 SDK 或恢复旧项目。

正文用小表说明先保存什么、怎样保存。技术入口、代码依赖、聊天定位和文件来源统一放附录，让需要继续开发的人能查到。影响后续使用的实际缺失，直接说明要补什么；不要另写一长串免责说明。

本次成果为一份 Markdown 文档。留存安排写明建议合并到哪些现有知识库、项目文档或规则，提供具体文案与入口，并区分仅建议、已合并和待批准。用户可以自行处理，也可以授权协助合并；按 [knowledge-handoff.md](knowledge-handoff.md) 执行，不自动拆分条目或另建经验库。

## 交付检查

- 关键历史在经验和模块之前，读者能理解项目如何走到当前状态。
- 正文中的技术问题均说明了具体影响，代码名和运行细节已集中到附录，删去反复限定范围的尾句。
- 每条主要判断能回到具体证据；推断和建议没有伪装成已验证事实。
- 成果能用于下一次行动，模块可定位并有依赖和边界，不是空泛感想或只有文件名的目录。
- 失败、未进入的阶段、人工辅助和未覆盖的范围如实记录；没有用旧成功结论覆盖后来的失败。
- 来源项目与历史没有因生成报告而被修改，规则建议与实际写入的状态明确。
