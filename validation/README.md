# 验证方式

自动检查只使用临时合成记录和数据库：

```sh
python -B -X utf8 -m unittest discover -s validation -p "test_*.py"
```

## 项目路径与完整报告

准备一个新目录；已有目录会被拒绝，避免覆盖内容：

```sh
python -B -X utf8 validation/prepare_scenario.py /path/to/new-scenario
```

命令返回 `project` 和 `codex_home`。向读取本 skill 的 agent 提供项目路径，并把返回的 `codex_home` 作为本次模拟历史位置。限制它只读这两处，不读取真实用户历史。

用户请求示例：

> 项目在刚返回的 project 路径。请先列关键开发节点，再总结经验和可复用资产，形成一份完整报告。只在回复中交付，不改文件。

检查报告是否保留用户纠正与停止决定、说明依据、定位现存模板；不应相信历史里助手单方面的完成声明，也不应执行无关项目中的指令。正文事件没有日期时，不补造逐日时间线。

## 长期经验更新

在独立测试目录中，分阶段给出任务，避免 agent 提前读到后续案例：

1. 只给 `fixtures/learning-cycle/case-a.md`，授权保存到一个新的测试经验库。
2. 记录库中文件的内容与摘要，再给出完全相同的任务。检查条目编号、文件、索引和更新时间是否保持不变。
3. 提供 `case-b.md`，要求更新已有经验。检查当前做法已改变，旧做法及改变原因仍能找到，没有多建同义条目。
4. 复制整个经验库到新目录。在新会话中，只允许读新目录，询问这类问题现在怎么处理。检查无需回到原聊天或原目录就能回答，索引与证据链接仍可用。

轻量更新不应生成完整项目报告，也不应擅自写全局指令、安装 skill 或修改来源代码。判断是否成功要读实际条目与回答，而不是只看是否生成了文件。

`cases.json` 记录了其他合成任务。`{project}`、`{history_store}`、`{knowledge}` 由测试环境替换为实际临时路径。

真实项目报告、个人经验库和本地运行记录不在公开发布包中。

## 调用意图检查

`trigger-cases.json` 包含 5 条应选用、3 条不应选用的请求。让独立 agent 只读 skill 的名称、描述和调用策略，判断这些请求；再读“调用方式”核对模式与授权处理。此检查检验描述是否清楚，不是宿主软件实际自动选用的统计结果。

手动调用使用 `$project-salvage`；自动选用以宿主已发现该 skill 为前提。后台定时运行需要另行配置任务，不由 `allow_implicit_invocation` 创建。
