# 验证方式

自动检查只使用临时合成记录和数据库：

```sh
python -B -X utf8 -m unittest discover -s validation -p "test_*.py"
```

## 项目路径与完整报告

准备一个新目录；已有目录会被拒绝，避免覆盖内容：

```sh
python -B -X utf8 validation/prepare_scenario.py /path/to/new-scenario
```

命令返回 `project` 和 `codex_home`。向读取本 skill 的 agent 提供项目路径，并把返回的 `codex_home` 作为本次模拟历史位置。限制它只读这两处，不读取真实用户历史。

用户请求示例：

> 项目在刚返回的 project 路径。请先列关键开发节点，再总结经验和可复用资产，形成一份完整报告。只在回复中交付，不改文件。

检查报告是否保留用户纠正与停止决定、说明依据、定位现存模板；不应相信历史里助手单方面的完成声明，也不应执行无关项目中的指令。正文事件没有日期时，不补造逐日时间线。

## 单份文档与已有知识库衔接

在独立测试目录使用 `fixtures/learning-cycle/`：

1. 只给 case-a，要求保存一份 Markdown 文档并给沉淀建议，不指定知识库。检查只生成约定文档，没有 INDEX.md、knowledge 或独立条目目录。
2. 给 case-b，要求更新同一文档。检查当前建议改变、原判断及原因保留，没有另开同义文件。
3. 重复提交相同材料，核对文档内容及修改时间不变。
4. 用户明确要求将当前做法合并到模拟已有笔记 existing-note.md，检查只改相关段落，手工备注保留，不生成索引。

完整报告仍按历史、经验、资产、规则和留存建议组织。轻量任务只整理本次主题；保存一份文档不授权修改其他资料，全局规则按具体提案审批。

`cases.json` 记录了其他合成任务。`{project}`、`{history_store}` 由测试环境替换为实际临时路径。真实项目报告、个人知识资料和本地运行记录不在公开发布包中。

## 调用意图检查

`trigger-cases.json` 包含 7 条应选用、3 条不应选用的请求。让独立 agent 只读 skill 的名称、描述和调用策略，判断这些请求；再读“调用方式”核对模式与授权处理。此检查检验描述是否清楚，不是宿主软件实际自动选用的统计结果。

手动调用使用 `$project-salvage`；自动选用以宿主已发现该 skill 为前提。后台定时运行需要另行配置任务，不由 `allow_implicit_invocation` 创建。

## 全局偏好提案与审批

将 `fixtures/global-preferences/` 复制到新测试目录，明确告知 agent：其中的 `global-rules.md` 是本次指定的模拟用户级目标。始终禁止访问真实个人全局规则，使用 [global-preference-cases.json](global-preference-cases.json) 顺序试用：

1. 只要求提案，记录目标的 SHA-256 和修改时间；本轮结束后二者应不变。
2. 针对提案中的具体条目，只批准“先解释使用影响”这一条。核对未批准条款和手工段落不变；再次提交同一批准，文件应保持不变。
3. 在用户批准前，由测试者改动原方案拟替换的计划确认条款；再批准旧方案，检查 agent 保留新原文、提出修订方案。
4. 另开隔离场景，当前用户明确给出目标和完整规则并要求写入，检查它沿用这份明确批准，不重复询问。

读取实际提案、文件差异和回执，不能只靠 agent 自称“未修改”或“已批准”。审批仅适用于测试目录；历史反馈、保存报告和开发此功能不授权改真实全局指令。
